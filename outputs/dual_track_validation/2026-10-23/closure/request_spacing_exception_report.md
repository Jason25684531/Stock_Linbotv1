## 2. 根因調查

**機制（已確認）**：
- `LoggedGate.wait()` 先呼叫 `RequestGate.wait()`（以單調時鐘睡到距離上一次放行滿 3.2 秒），再呼叫 `odr.log()`；`log()` 先開檔、再用 `datetime.now()` 取時間、最後寫入。
- 所以 ledger 的 `ts` 是**放行之後才取得的牆上時鐘時間**，它等於「閘門放行時刻 ＋ 開檔與取時間的延遲」；舊 ledger 沒有記錄閘門自己量到的間隔。
- 因此記錄間隔 ＝ 3.2 ＋（本筆延遲 − 上一筆延遲）。實測 1,833 個間隔的 (間隔 − 3.2) 中，1%～99% 落在 −0.013～+0.026 秒，最大 +0.386 秒，最小 −0.266 秒；也就是說上下兩側都有同量級的離群值，與「記錄延遲的抖動」一致。

**未能證明的部分**：
- 2.934 秒對應約 0.27 秒的記錄延遲或牆上時鐘調整。我在閒置的本機上量測 4,000 次附加寫入，最大延遲只有 3.6 毫秒，遠小於 266 毫秒；所以 0.27 秒的停頓**不是**閒置機器上的常態。下載當時機器是否有其他負載（掃毒、磁碟競爭、時間同步）無法從現有紀錄還原。
- 舊 ledger 沒有請求真正送出的時間，也沒有閘門量到的間隔，因此**這一次放行的實際間隔無法事後證明是 ≥ 3.2 秒，也無法證明 < 3.2 秒**。
- Windows 時間服務事件的查詢沒有回傳任何事件；這不等於沒有時鐘調整，只是沒有證據。

**結論**：最可能的原因是放行時間戳的記錄延遲（或時鐘調整），而不是閘門放行過早；但這個結論是推論，不是證明。
