# Feature Specification: TWSE MCP Server 路由標準化

**Feature Branch**: `004-standardize-mcp-routes`  
**Created**: 2026-04-08  
**Status**: Draft  
**Input**: User description: "建立「TWSE MCP Server 路由標準化」規格：新增 `/v1/tools/get_company_basic_info`、`/v1/tools/get_market_statistics`、`/v1/tools/get_foreign_investment` 路由，讓 `tool/mcp_client.py` 可以直接命中標準端點，不再依賴 fallback 降級機制。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 讓 MCP Client 直接命中標準工具路由 (Priority: P1)

作為系統維運與整合開發人員，我需要 MCP Server 提供穩定且明確的標準工具路由，讓 client 可以直接呼叫預期端點，不必先嘗試失敗再降級到舊路由。

**Why this priority**: 這是此次功能的核心價值。只要標準路由沒有落地，client 仍必須保留 fallback，系統整體契約就不算真正穩定。

**Independent Test**: 直接對三個新路由發送合法請求，驗證 server 可回傳與既有資料契約一致的成功回應，且 client 不需降級即可完成查詢。

**Acceptance Scenarios**:

1. **Given** MCP Server 已部署新標準工具路由，**When** client 呼叫市場摘要端點，**Then** server 應直接回傳可用資料，而不是依賴舊路由轉接後才成功。
2. **Given** MCP Server 已部署新標準工具路由，**When** client 呼叫籌碼或公司基本資訊端點，**Then** server 應以既有資料語義回傳結果，讓下游不需改寫資料消費方式。

---

### User Story 2 - 保持新舊路由回應契約一致 (Priority: P2)

作為整合維護者，我需要新標準工具路由與既有服務行為保持一致，讓 server 在增加新路由後，不會產生兩套互相衝突的資料格式或錯誤語意。

**Why this priority**: 若新路由與舊路由回應語意不一致，雖然 client 可以直接命中新路由，但整體系統仍會因資料格式分裂而增加維護成本與回歸風險。

**Independent Test**: 針對同一組輸入分別驗證新標準路由與現有資料契約，確認成功回應欄位、錯誤結構與驗證規則維持一致。

**Acceptance Scenarios**:

1. **Given** 同一個查詢條件可透過標準工具路由處理，**When** server 回應成功結果，**Then** 回應欄位意義與既有資料契約必須一致。
2. **Given** 請求缺少必要條件，**When** 呼叫任一新標準工具路由，**Then** server 應回傳一致且可預期的驗證錯誤格式。

---

### User Story 3 - 降低日後整合與診斷成本 (Priority: P3)

作為後續功能開發者，我希望標準工具路由名稱本身就能明確對應查詢意圖，讓除錯、文件維護與新功能整合更直接，不必依賴額外的 fallback 邏輯判斷實際命中的端點。

**Why this priority**: 這項工作雖不直接改變終端使用者介面，但能降低整合複雜度，讓後續 server 與 client 演進更可控。

**Independent Test**: 閱讀操作文件與服務日誌時，可直接辨識查詢意圖與實際命中路由，且開發者不需額外追查 fallback 是否介入。

**Acceptance Scenarios**:

1. **Given** 新的查詢功能需要接入 MCP Server，**When** 開發者查看標準路由列表，**Then** 能直接找到與查詢意圖對應的工具端點名稱。
2. **Given** 一次查詢失敗需要排查，**When** 維運人員查看日誌或回應內容，**Then** 能直接判斷是標準工具路由本身的問題，而不是 fallback 鏈路中的模糊失敗。

### Edge Cases

- 若新標準工具路由收到缺少必要欄位的請求，server 必須回傳一致的驗證錯誤，而不是回傳空成功結果。
- 若新標準工具路由與既有舊路由都存在，系統必須避免兩者回傳不同欄位語義或不同錯誤結構。
- 若公司基本資訊查詢指定的標的不存在，server 必須回傳可識別的失敗結果，不得回傳不屬於請求標的的資料。
- 若上游資料暫時不可用，新標準工具路由必須保留可重試的失敗語意，不能把上游故障誤包裝為正常空資料。
- 若新路由已可用，client 端後續整合不得再以「先失敗再降級」作為正常成功路徑。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統必須提供三個標準工具路由，分別對應公司基本資訊、市場摘要與外資籌碼查詢。
- **FR-002**: 三個標準工具路由必須能被 `tool/mcp_client.py` 直接呼叫，作為對應查詢能力的正式首選入口。
- **FR-003**: 新標準工具路由的成功回應必須維持與既有資料契約相容，使現有 client 與下游邏輯不需要因回應語義改變而重寫。
- **FR-004**: 新標準工具路由必須對必填參數執行一致的輸入驗證，並在請求不合法時回傳可預測的錯誤結果。
- **FR-005**: 新標準工具路由必須在上游資料來源失敗時回傳可重試的失敗語意，而不是將失敗誤表示為正常空資料。
- **FR-006**: 新標準工具路由的資料主題必須與路由名稱一一對應，避免一個路由承載多種不明確查詢意圖。
- **FR-007**: 公司基本資訊標準工具路由必須只回傳與指定標的相關的資料，不得混入其他標的內容。
- **FR-008**: 市場摘要標準工具路由必須提供可支援大盤或市場概況統計所需的標準化資料集合。
- **FR-009**: 外資籌碼標準工具路由必須提供可支援外資淨買賣超查詢的標準化資料集合，且在有相關資料時可延伸包含其他法人欄位。
- **FR-010**: 新標準工具路由落地後，client 的 fallback 降級機制不得再被視為正常依賴路徑，而應僅作為過渡或異常保護。
- **FR-011**: 新標準工具路由與既有舊路由若同時存在，必須維持一致的回應欄位意義與錯誤語意，避免服務契約分裂。
- **FR-012**: 任何新增的標準工具路由都必須同步反映在服務文件或操作說明中，讓後續整合者可直接辨識可用端點。

### Key Entities *(include if feature involves data)*

- **Tool Route Request**: 表示對標準工具路由發送的一次查詢請求，關鍵屬性包含查詢主題、必要參數、目標標的或日期，以及請求識別資訊。
- **Tool Route Response**: 表示標準工具路由回傳的成功資料，關鍵屬性包含資料主題、資料日期或期間、記錄集合與回應筆數摘要。
- **Validation Error Result**: 表示因輸入不合法而產生的失敗結果，關鍵屬性包含錯誤代碼、錯誤訊息、是否可重試與診斷資訊。
- **Upstream Failure Result**: 表示上游資料暫時不可用時的失敗結果，關鍵屬性包含失敗主題、是否可重試與關聯識別資訊。
- **Route Intent Mapping**: 表示每個標準工具路由與查詢主題的一對一對應關係，關鍵屬性包含路由名稱、資料主題與預期消費端。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 三個標準工具路由在驗收測試中 100% 可被 client 直接呼叫成功，不需要先觸發 fallback 才取得資料。
- **SC-002**: 對相同輸入進行驗收時，新標準工具路由的成功回應與既有資料契約在必要欄位與欄位意義上達成 100% 一致。
- **SC-003**: 對缺少必要參數的測試請求，三個標準工具路由都能在 100% 的案例中回傳一致的驗證錯誤結構。
- **SC-004**: 在模擬上游暫時失敗的測試中，三個標準工具路由都能在 100% 的案例中回傳可重試的失敗語意，而非正常空結果。
- **SC-005**: 路由標準化完成後，client 正常查詢日誌中不再需要依賴 fallback 路徑作為成功主流程。

## Assumptions

- 既有 MCP Server 已經具備與三個查詢主題對應的資料取得能力，本次重點是將其公開為更明確的標準工具路由。
- 既有 client 與下游邏輯維持目前資料契約不變，本次不重新定義資料模型或資料表結構。
- 新增標準工具路由不代表必須立即移除舊路由，但舊路由若保留，必須維持與新路由相容的語意。
- 本次規格聚焦於 server 路由標準化與契約一致性，不包含新的資料來源、新的前端功能或新的商業查詢主題。
